# Codex Test Prompt

Работай в этом репозитории как senior Rust engineer.

Контекст проекта:
- Это Rust backend на axum + SeaORM.
- Основные интеграционные тесты лежат в `api/tests/*.rs`.
- Общие тестовые helper-ы лежат в:
  - `api/tests/common/mod.rs`
  - `api/src/test_support.rs`
- Тесты должны быть интеграционными HTTP-тестами через реальный `axum Router`, а не unit-тестами.
- Используется реальная dev Postgres в Docker.
- Redis и SMTP в тестах сейчас не тестируются, для них уже есть test bypass через env:
  - `DISABLE_SMTP=true`
  - `DISABLE_REDIS_STREAM=true`
- Перед тестами используется очистка dev БД через существующий test bootstrap.
- Если нужно добавить сиды для тестов, расширяй `api/src/test_support.rs`.
- Каждый API-модуль должен покрываться отдельным файлом в `api/tests/<module>.rs`.
- Следуй уже существующему стилю тестов в репозитории, не придумывай новый формат.
- Если находишь баг в сервисе во время написания тестов, не скрывай его и не подгоняй тест под неправильное поведение. Сначала коротко объясни баг, потом предложи или внеси фикс, если я не запретил менять сервис.
- Если я явно прошу только тесты, не меняй production-код без необходимости. Если без фикса тест не может быть доведен до рабочего состояния, укажи это явно.
- Перед изменениями сначала изучи существующие handler/service/dto/entity/test файлы конкретного модуля.
- После изменений обязательно запусти релевантные тесты и сообщи результат.
- Если API изменился, сначала обнови существующие тесты под новое поведение, затем добавь недостающие сценарии.
- Не смешивай разные домены в одном test-файле без причины.
- Если маршрут не опубликован в handler/router, не пиши на него HTTP-тест как на публичный API.
- Используй существующие helpers `setup`, `login_and_get_cookies`, `json_body`, `unique_email`.
- Для ручных правок файлов используй `apply_patch`.

Что нужно сделать:
1. Сначала проанализируй текущую реализацию целевого модуля.
2. Найди существующие тесты для него или отсутствие тестов.
3. Если тестов нет, создай отдельный файл `api/tests/<module>.rs`.
4. Если тесты уже есть, обнови их под текущий API.
5. Добавь только полезные интеграционные сценарии:
   - auth required
   - happy path
   - forbidden/role checks
   - validation/bad request
   - not found, если релевантно
   - обновление/удаление/связанные сущности, если модуль это поддерживает
6. Если нужны новые сиды, добавь их в `api/src/test_support.rs`.
7. Запусти точечные тесты по модулю.
8. В конце дай краткий отчет:
   - какие файлы изменены
   - какие сценарии покрыты
   - какие тесты прошли
   - есть ли найденные баги или оставшиеся риски
